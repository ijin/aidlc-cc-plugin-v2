# Working in this repo (agent guide)

This repo publishes the Claude Code plugin `aidlc-v2`, which sets up
[awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows) v2 in a user's project by
driving upstream's own installer and `aidlc config`, pinned to one verified upstream release. Read
`README.md` for the full picture and `.design/upstream-installer-shim.md` for the design; this file
is the short list of **rules and invariants**.

This file is **committed and public** — keep it environment-neutral (no machine paths, tooling, or
provider names). Local workflow notes go in `CLAUDE.local.md` (gitignored).

## Layout & the build model

- The plugin ships **no upstream code**. `UPSTREAM.lock` pins the upstream release (tag, peeled
  commit, installer and checksum hashes). It is rewritten only by
  `targets/claude/sync-upstream.sh` — **never hand-edit it**.
- `dist/claude/` is the **built, committed plugin** — the only thing that ships. It is generated by
  `targets/claude/build.mjs` from the lock and the authored files in `targets/claude/plugin/`
  (entry skill, the `scripts/aidlc-v2.sh` helper, legacy-migration data). **Never hand-edit
  `dist/`** — change the sources and rebuild, and commit `dist/` in the same change
  (`node targets/claude/build.mjs`). A pre-commit hook and CI enforce freshness;
  `git config core.hooksPath .githooks` enables the hook.
- `targets/claude/plugin/data/legacy-2.1.4.*` describe exactly what this plugin's 2.1.4 release
  installed into projects. They are historical facts — never regenerate them from anything but the
  `v2.1.4+up.b61e0ed` tag.

## Invariants of the helper (`scripts/aidlc-v2.sh`)

Break one of these and the plugin can damage a user's project or machine:

- Never pass `--force` to `aidlc config` (it silently replaces user files) and never pass
  `--profile` to upstream's installer (it edits shell startup files).
- Never run an installer whose SHA-256 differs from the pinned hash; never update, replace, or
  re-point a user's existing `aidlc` CLI (pin the project instead).
- Legacy migration removes only regular files whose hash matches the 2.1.4 manifest, never
  through a symlink, never outside the project, never under `aidlc/`.
- Every `aidlc` call has stdin redirected — no interactive prompt may hang the Bash tool.
- Exit codes are a contract with the entry skill (0 ok, 1 error, 2 usage, 3 conflicts,
  4 integrity, 5 user action). Change them in both places or neither.
- POSIX `sh` only, no runtime beyond standard tools — it must run under macOS `/bin/sh`, Linux
  `dash`, and Git Bash on Windows.

## Adopting an upstream release

- Use **`./targets/claude/sync-upstream.sh <tag>`** (or the `release-upstream` skill). Stable tags
  only unless a preview is explicitly wanted (`--allow-preview`).
- The **plugin version mirrors the pinned upstream version** (`2.10.0`, or `2.10.0-pN` for
  plugin-only fixes); the build enforces it against `package.json` and `marketplace.json`.
- The decision to adopt is human; only the mechanics are automated. Read upstream's changelog for
  anything touching `aidlc config` flags, exit codes, install locations, or the stamp file.

## Verification (before claiming done)

- `npm test` — free and deterministic: build-contract drift injection, the helper against a fake
  release and stub CLI, dist freshness. **Always green before committing.**
- `npm run gate` — the real pinned release in a sandbox (network): fresh and legacy projects end
  in a clean upstream `doctor`. **Run before every release** and after changing the helper.
- `npm run smoke` — one billable call: the plugin loads and exposes exactly `aidlc-v2:aidlc`.
- Windows is covered only by stubbed tests; say so rather than claiming it works.

## How to make changes here

- **Independent review is part of "done."** For any substantive change (the helper, the build
  contract, sync, the tests): make the change → independent adversarial review → explicit
  agreement → then it's done.
- If a change seems to require patching upstream's files in a user's project, it belongs upstream
  instead.
- Validate workflow YAML with `actionlint`; blank lines must be completely empty; no backslash
  line continuations.

## Public-repo hygiene

- Commit messages are **plugin/release-focused, for an outside reader** — no internal process or
  tooling framing.
- Keep the README's License & attribution section accurate. This is an independent community
  project, not affiliated with AWS.
